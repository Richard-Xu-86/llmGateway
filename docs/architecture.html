System design

LLM Gateway

An authenticating proxy in front of the OpenAI API that records every request and response, streams the answer back untouched, and a dashboard for inspecting the traffic live.

hot path — a person is waiting on this cold path — can fail without anyone noticing
The central decision

Two paths that must never become one

Every other choice in this system falls out of keeping these apart. The proxy is on the critical path; the logging deliberately is not.

Hot path

Your app is blocked on this. Every millisecond spent here is a millisecond a user spends looking at a spinner.

  • Authenticate, swap the key, forward
  • Push each SSE frame through the instant it lands
  • sink.write() returns void — it cannot be awaited, so it cannot slow anything down
  • A logging failure is caught and swallowed; it never becomes a caller-facing error

Cold path

Nobody is waiting. It can be slow, it can retry, it can be down for an hour, and no request ever fails because of it.

  • Records batch up and ship on a 250 ms timer
  • Backend down? The batch goes back on the queue and tries again
  • Queue full? Oldest records drop — and the count is surfaced, so the loss is visible rather than silent
  • Measured: a log arrived 98 ms after the caller already had its last token

Why four endings and not two

A 200 can be a lie

On a streamed response the status code is committed before the answer exists. Anything that goes wrong afterwards still arrives under a 200 OK — which is exactly the failure a status-code logger cannot see.

Terminal stateWhat happenedStatus on the wire
completed The [DONE] sentinel arrived. The answer is whole. 200
truncated Frames simply stopped and no [DONE] ever came. Nobody raised an error anywhere. 200 — misleading
upstream_error An error object arrived inside a frame, after the headers were already sent. 200 — misleading
client_aborted The caller hung up mid-stream. The upstream request is cancelled too, so generation stops being billed. 499

On the non-streaming path only the first and third are reachable: await upstream.text() either returns the whole body or throws. You cannot half-succeed at a lump. Streaming is the only mode that needed four.

Known gap: rejected keys leave no trace.

The auth check returns at line 60; the log emitter isn't constructed until line 130. So a 401 short-circuits before anything can be recorded — and "someone is trying keys against my gateway" is precisely what an inspector should surface. The fix is small: move the check below emit and write a row with a null apiKeyId. Worth naming out loud rather than leaving to be found.

One system, three configurations

The seam that lets you test is the seam that lets you swap providers

Nothing in the code knows which mode it is running in. The gateway cannot tell OpenAI from a pretend OpenAI on port 4010, and the proxy logic does not change when the log destination does.
